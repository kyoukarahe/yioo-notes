# Yioo Notes 한국어 교정·용어 기준

- Status: active
- Applies to: Yioo Notes 초고, 제목, 요약, 도표 문구, 게시 전 검수
- Last updated: 2026-08-17

## 이 문서의 역할

이 문서는 Yioo Notes가 한국어 문장을 쓰고 고칠 때 따르는 편집
기준이다. 맞춤법만 고치는 문서도 아니고, 모든 문장을 짧게 만드는
문서도 아니다. 독자가 한 번에 뜻을 파악할 수 있도록 문장 구조와
용어를 고치되, 사실관계와 기술적 구분은 그대로 보존하는 것이
목적이다.

`humanize-korean`과 이 문서는 역할이 다르다.

- `humanize-korean`은 번역투, 반복되는 리듬, 기계적 병렬, 피동 표현 등
  문체의 어색함을 찾고 다듬는다.
- 이 문서는 어떤 용어를 쓸지, 영어 표현을 직역해도 되는지, 새로 만든
  분류를 통용되는 전문용어처럼 쓰고 있지는 않은지를 판단한다.
- 문체가 자연스러워도 용어가 부정확할 수 있고, 용어가 정확해도 문장이
  어려울 수 있다. 두 검사를 모두 통과해야 한다.

## 기본 원칙

### 1. 결론을 먼저 쓰고 조건을 뒤에 붙인다

주어와 핵심 동사가 나오기 전에 조건, 예외, 수식어가 여러 겹 쌓이면
문장을 나눈다. 독자가 문장 끝까지 가야만 뜻을 알 수 있는 구조를 피한다.

나쁜 예:

> 완료는 의도한 결과가 의도한 진입점에서 도달 가능하고, 필요한 변화가
> 실제로 남았으며, 그 결과를 판정할 권위 있는 곳에서 다시 확인된 상태다.

권장 예:

> 에이전트가 완료했다고 말하는 것만으로는 부족하다. 사용자가 실제
> 경로에서 결과에 도달할 수 있어야 한다. 변경 내용이 남아 있는지,
> 최종 결과를 보여 주는 화면이나 저장소에서도 다시 확인해야 한다.

### 2. 한 문장에는 중심 주장 하나만 둔다

원인, 결과, 예외, 반론이 모두 중요하다면 쉼표로 연결하지 말고 문장을
나눈다. 문장을 나눈 뒤에도 논리 관계가 보이도록 `그래서`, `다만`,
`반면` 같은 연결어를 필요한 곳에만 쓴다.

### 3. 추상명사를 사람과 행동으로 바꾼다

`가능성의 확인`, `권위의 판정`, `결과의 유지`처럼 명사만 이어지면 누가
무엇을 하는지 흐려진다. 의미가 허용하는 범위에서 주체와 동사를 밝힌다.

- `결과의 검증이 필요하다` → `사용자가 결과를 다시 확인해야 한다`
- `권한의 분리가 요구된다` → `실행 권한과 승인 권한을 나눠야 한다`
- `상태의 지속성을 보장한다` → `작업을 다시 열어도 같은 상태가 남아야 한다`

### 4. 쉬운 문장이 정확성을 지우지 않게 한다

문장을 쉽게 고치면서 날짜, 수치, 범위, 예외, 불확실성, 출처, 인용,
기술적 차이를 삭제하지 않는다. 긴 문장을 둘로 나눌 수는 있지만 두
문장이 원래와 다른 주장을 해서는 안 된다.

### 5. 이유를 함께 쓴다

같은 요청도 이유가 없으면 다르게 해석될 수 있다. 규칙이나 권고를 쓸
때는 그것이 막으려는 실패나 지키려는 가치를 함께 설명한다.

나쁜 예:

> UI는 반드시 상태표를 작성해야 한다.

권장 예:

> 사용자가 길을 잃거나 되돌리기 어려운 화면 전이는 상태와 복구 방법을
> 적어 둔다. 구현자마다 오류 화면과 취소 동작을 다르게 해석하는 일을
> 막기 위해서다.

## 영어 기술어를 고르는 방법

영어 단어가 실제로 존재한다는 사실만으로 한국어 직역이 자연스러워지는
것은 아니다. 용어를 쓰기 전에 다음 네 종류 가운데 어디에 해당하는지
판단한다.

| 종류 | 판단 기준 | 쓰는 방법 |
| --- | --- | --- |
| 정착된 표준 용어 | 표준, 공식 문서, 교과서에서 같은 뜻으로 반복 사용 | 통용되는 한국어를 쓰고 필요하면 첫 등장에 영어 병기 |
| 업계에서 널리 쓰는 용어 | 여러 회사와 실무 문서에서 대체로 같은 뜻으로 사용 | 한국어로 먼저 설명하고 영어를 한 번 병기 |
| 형성 중인 용어 | 최근 제안이나 일부 제품·프로젝트에서만 사용 | 누가 제안했는지와 적용 범위를 밝히고 보편 표준처럼 쓰지 않음 |
| 이 글의 편집 표현 | 여러 개념을 설명하려고 글에서 새로 묶은 이름 | 쉬운 한국어를 우선하고 `이 글에서는`이라고 범위를 밝힘 |

### 용어 확인 질문

1. 정확한 영어 원어는 무엇인가?
2. 표준이나 공식 문서가 같은 뜻으로 사용하는가?
3. 한 프로젝트의 제품명이나 특정 저자의 표현은 아닌가?
4. 한국어 기술 문서에서는 실제로 어떻게 부르는가?
5. 직역했을 때 법률, 행정, 철학 등 다른 분야의 뜻이 먼저 떠오르지 않는가?
6. 영어를 빼고 한 문장으로 풀어 써도 뜻이 유지되는가?
7. 이 글에서 만든 분류라면 그 사실이 드러나는가?

검색 결과의 제목이나 요약만 보고 용어를 확정하지 않는다. 가능하면
표준, 공식 문서, 원 논문을 직접 읽고 뜻과 적용 범위를 확인한다. 용어가
시점에 따라 바뀔 수 있으면 확인 날짜도 원장에 남긴다.

## `contract`를 번역하는 기준

소프트웨어에서 `contract`는 법률 문서만 뜻하지 않는다. 보통 한쪽이
충족해야 할 조건과 다른 쪽이 보장해야 할 결과를 묶어 부르는 비유다.
그러나 이를 언제나 `계약`으로 옮기면 일반 독자에게 법률 용어처럼
들리거나, 글에서 새로 만든 분류가 정식 표준처럼 보일 수 있다.

| 영어 표현과 문맥 | 권장 표기 | 비고 |
| --- | --- | --- |
| legal contract | 계약 | 실제 법률 관계를 다룰 때 |
| Design by Contract | 계약에 의한 설계 | 고유한 소프트웨어 설계 개념이므로 첫 등장에 원어 병기 |
| API contract | API 명세, API가 보장하는 조건 | 개발자 대상 글에서는 `API 계약`도 가능 |
| data contract | 데이터 계약 | 먼저 스키마·의미·품질·최신성에 관한 합의라고 설명 |
| UI behavior contract | UI 동작 명세, 상태·동작 규칙 | 보편적인 UI 표준명처럼 쓰지 않음 |
| capability contract | 에이전트 사용 조건, 능력·권한 범위 | 특정 제안의 이름이 아니라면 쉬운 한국어 우선 |
| authority contract | 권한과 승인 규칙 | `권위 계약`이라는 직역은 피함 |
| lifecycle contract | 도입·변경·종료 규칙 | 무엇의 생애주기인지 구체적으로 씀 |
| instruction contract | 지침의 적용 순서와 범위 | 문맥에 따라 `지침 규칙` 또는 풀어쓰기 |

따라서 Yioo Notes에서는 다음처럼 고친다.

- `네 가지 계약` → `네 가지 확인 항목` 또는 `네 가지 경계`
- `기능 계약` → `기능 범위`
- `권위 계약` → `권한과 승인`
- `데이터 계약` → 정식 용어를 설명하는 문맥이면 유지, 아니면 `데이터 처리 규칙`
- `생애주기 계약` → `도입·변경·종료 규칙`
- `capability contract card` → `에이전트 사용 조건표`
- `UI 행동 계약` → `UI 동작 명세` 또는 `상태·동작 규칙`

`계약`을 유지해야 할 때는 첫 등장에 뜻을 바로 설명한다.

> 데이터 계약(data contract)은 데이터 생산자와 사용자가 스키마, 의미,
> 품질, 최신성 기준을 미리 합의해 둔 것이다.

### 참고한 공식 용례

- Eiffel의 Design by Contract 설명은 `contract`를 호출자와 제공자의 기대와
  보장으로 정의한다: <https://www.eiffel.org/doc/eiffel/ET-_Design_by_Contract_%28tm%29%2C_Assertions_and_Exceptions>
- Microsoft의 API contract 설명은 관련 API 묶음과 그것이 제공하는 보장을
  가리킨다: <https://learn.microsoft.com/en-us/archive/msdn-magazine/2015/windows-10-special-issue/ui-design-adaptive-apps-for-windows-10>
- Google Cloud의 data contract 사례는 생산자와 사용자 사이의 기계 판독
  가능한 합의로 정의한다: <https://cloud.google.com/blog/products/data-analytics/vmo2-uses-data-contracts-to-build-scalable-ai-and-data-products>
- AI 에이전트의 `capability contract`는 개별 IETF 초안 등에서 등장하지만
  아직 형성 중인 표현으로 다룬다: <https://datatracker.ietf.org/doc/html/draft-sunyi-hacp-protocol-00>

## `cheap`, `reasonable`, `evidence`를 번역하는 기준

영어의 한 단어가 한국어의 한 단어와 항상 대응하지는 않는다. 특히 비용과
검증을 다루는 글에서는 직역보다 문장에서 맡는 역할을 먼저 본다.

### `cheap`과 `reasonable`

`싼`, `싸다`는 가격이 낮다는 뜻만이 아니라 품질이 낮거나 비용을 무리하게
줄였다는 부정적인 느낌을 줄 수 있다. 그 느낌이 필요한 문맥에서만 쓴다.
`reasonable`이나 중립적인 `low-cost`를 옮길 때는 선택의 이유를 드러내는
표현을 고른다.

| 뜻과 문맥 | 먼저 검토할 표현 |
| --- | --- |
| 품질 저하나 무리한 절감을 비판 | 싼, 값싼, 싸구려, 비용만 줄인 |
| 비용이 비교적 낮다는 중립적 사실 | 비용이 낮은, 부담이 적은, 적은 비용으로 가능한 |
| 조건과 비용을 함께 고려한 선택 | 합리적인, 현실적인, 비용 대비 나은 |
| 장기간 총비용을 줄임 | 경제적인, 운영 부담이 적은, 총비용이 낮은 |

예를 들어 `the cheapest option`이 단순히 네 방법 가운데 자원이 가장 적게
드는 방법을 뜻한다면 `가장 싼 방식`보다 `조건에 맞는 가장 합리적인 방식`
또는 `비용 부담이 가장 적은 방식`이 자연스럽다. 원문이 품질을 희생한
절감을 비판할 때만 `싼 방식`을 유지한다.

### `evidence`

`증거`는 법률·수사·포렌식 문맥에서는 정확한 말이지만, 일반적인 제품 글과
에세이에서는 딱딱하거나 범죄를 입증하는 자료처럼 들릴 수 있다. 무엇을
위해 남기는 정보인지에 따라 더 구체적인 말을 쓴다.

| `evidence`가 하는 일 | 먼저 검토할 표현 |
| --- | --- |
| 주장을 뒷받침 | 근거, 자료, 출처 |
| 작업이 끝났음을 남김 | 완료 기록, 처리 기록 |
| 저장소나 API에서 다시 확인 | 확인 결과, 재확인 결과 |
| 시험이나 검사 결과 | 검증 결과, 검사 결과 |
| 통과 여부를 판정 | 판단 기준, 확인 항목 |
| 감사·추적에 사용 | 작업 기록, 변경 이력, 감사 기록 |
| 법률·수사·포렌식에서 사실을 입증 | 증거 |

기계적으로 모두 바꾸지는 않는다. 학술 논증의 `empirical evidence`, 보안의
`cryptographic proof`, 법률상의 증거처럼 분야에서 굳어진 의미라면 정확한
전문용어를 우선한다. 반대로 `completion evidence`는 보통 `완료 기록`,
`evidence from readback`은 `재확인 결과`, `evidence supporting a claim`은
`주장의 근거`처럼 목적을 풀어 쓴다.

## 자주 직역되는 기술어

아래 표는 고정 번역 사전이 아니다. 문맥에 따라 더 구체적인 말을 고르기
위한 출발점이다.

| 영어 | 무조건적인 직역 | 먼저 검토할 한국어 |
| --- | --- | --- |
| authority | 권위 | 권한, 승인 주체, 최종 판정 기준 |
| authoritative source | 권위 있는 소스 | 기준 원본, 최종 판정에 쓰는 자료 |
| canonical source | 정규 소스 | 기준 원본, 정본 |
| capability | 능력 | 할 수 있는 일, 기능 범위 |
| surface | 표면 | 사용자에게 보이는 지점, 공개 영역, 적용 범위 |
| readback | 리드백 | 결과 재확인, 저장된 값 다시 읽기 |
| lifecycle | 생애주기 | 도입·변경·운영·종료 과정 |
| invariant | 불변식 | 항상 지켜야 할 조건; 수학·검증 문맥에서는 `불변식` 유지 |
| state | 상태 | 그대로 사용하되 무엇의 상태인지 밝힘 |
| workflow | 워크플로 | 작업 절차, 진행 순서; 제품 기능명이면 원어 유지 가능 |
| control plane | 제어면 | 관리 계층, 실행을 관리하는 부분; 네트워크 전문 문맥에서는 `제어 평면` |

영어 단어 하나에 한국어 하나를 고정하지 않는다. 문장의 독자와 분야,
정밀도 요구에 따라 가장 구체적인 표현을 선택한다.

## 제목과 결론 문장 점검

제목, 요약, 굵은 결론은 본문보다 엄격하게 점검한다.

- 제목만 읽어도 무엇을 다루는지 알 수 있는가?
- 멋있어 보이는 추상명사 때문에 실제 주제가 가려지지 않는가?
- 이 글에서 만든 표현을 이미 정착된 개념처럼 선언하지 않았는가?
- 한 번 읽고 주어, 행동, 결과를 파악할 수 있는가?
- 제목에서 쓴 핵심 용어를 본문 첫 부분에서 설명하는가?

예:

- `좋은 UI 명세는 화면 목록이 아니라 행동 계약이다`
  → `좋은 UI 명세는 화면 목록이 아니라 상태와 동작을 쓴다`
- `에이전트의 권위 계약을 설계하라`
  → `에이전트가 무엇을 할 수 있고 누가 승인할지 먼저 정하라`

## 초고와 게시 전 교정 절차

### 초고 전

1. 핵심 기술어와 영어 원어를 적는다.
2. 각 용어를 `표준 / 업계 용어 / 형성 중 / 편집 표현`으로 분류한다.
3. 일반 독자가 알아야 할 정의와 굳이 알 필요 없는 영어를 구분한다.

### 초고 작성 중

1. 자연스러운 한국어를 먼저 쓴다.
2. 영어가 정확성을 높일 때만 첫 등장에 괄호로 병기한다.
3. 글에서 만든 분류는 `이 글에서는`이라고 밝힌다.
4. 규칙에는 적용 이유와 막으려는 실패를 함께 쓴다.

### 한국어 윤문 후

1. 윤문 과정에서 기술어, 수치, 범위, 부정 표현이 바뀌지 않았는지 확인한다.
2. 제목, 요약, 굵은 결론을 따로 읽고 긴 수식 구조를 고친다.
3. 같은 영어 단어를 문맥과 무관하게 같은 한국어로 옮기지 않았는지 본다.
4. 정의하지 않은 신조어와 편집 표현을 찾는다.

### 게시 승인 전

1. 독자가 두 번 읽어야 이해할 문장을 표시한다.
2. 해당 문장을 줄이는 대신 먼저 둘로 나눠 본다.
3. 용어 원장의 분류와 본문 표현이 일치하는지 확인한다.
4. 사실을 쉽게 풀어 쓴 결과가 원래 주장보다 넓어지지 않았는지 확인한다.

## 용어 원장 템플릿

글마다 논쟁적이거나 낯선 핵심 용어가 있다면 비공개 source ledger에
다음을 남긴다.

| 항목 | 내용 |
| --- | --- |
| English term | 원어와 정확한 철자 |
| Korean wording | 본문에서 사용할 표현 |
| Status | 표준 / 업계 용어 / 형성 중 / 편집 표현 |
| Meaning in this article | 이 글에서 뜻하는 바 |
| Primary source | 표준, 공식 문서, 원 논문 |
| Checked date | 확인 날짜 |
| Avoid | 피할 직역이나 오해 가능성이 있는 표현 |

이 문서는 살아 있는 편집 기준이다. 반복해서 문제가 생긴 표현은 실제
초고의 공개 가능한 예와 함께 추가한다. 단일 글에서만 필요한 전문용어는
이 문서에 모두 넣지 말고 해당 글의 source ledger에서 관리한다.
